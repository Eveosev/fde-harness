# FDE Harness 交互与 UI 方案 A：静态产物型

**版本**：0.1（并行开发用）　**日期**：2026-11-25
**组合**：1C 静态 HTML + 答案文件回传　/　2C 宿主内摘要 + 独立页面详情　/　3B 本地记录 + 可导出验收单　/　4B 静态健康报告
**关联文档**：[PRD](01-product-requirements.md)、[架构](02-architecture.md)、[D01–D08 决策摘要](02-architecture.md#17-已采纳决策摘要与兼容约定)、[方案 B · 本地工作台](04-ui-workbench.md)
**一句话**：Harness 不起任何服务，只生成可离线打开的 HTML 产物，用户的回答以文件形式回传，由宿主导入。**不需要修订 D02。**

---

## 1. 定位与适用

| 项目 | 说明 |
|---|---|
| 适用场景 | 首批试点、安全要求严格或禁止本地服务的客户环境、Skill 在无 MCP 宿主中的降级运行 |
| 核心取舍 | 用“导出 / 导入一步”换取零服务、零端口、零额外攻击面 |
| 不做什么 | 不起本地 HTTP 服务；不在页面里放执行批准按钮；不做实时刷新 |
| 与方案 B 的关系 | 同一套数据契约、同一套前端组件。方案 B 在其上增加“本地服务 + 实时回写”，方案 A 是 B 的安全降级形态 |

## 2. 交互通道总览

沿用五通道模型（① 后台静默 ② 对话 ③ 宿主原生确认 ④ 只读可视化产物 ⑤ 交互式工作台）。**方案 A 不使用通道 ⑤**，它的功能由“④ + 答案文件”替代。

| 阶段 | 交互点 | 通道 | 方案 A 的实现 |
|---|---|---|---|
| 启动 | 选模式、说目标、授权范围 | ② + ③ | 对话；授权走宿主确认 |
| 探查 | 进度与发现概况 | ② 摘要 | 对话里给 5–8 行摘要和“查看详情”路径 |
| 建模 | 能力图 / ER 浏览 | ④ | `fde view graph` 生成 `graph.html` |
| 对齐 | 问题卡（少量，≤3 张） | ② | 对话内逐条问，附 example |
| 对齐 | 问题卡（批量，>3 张） | ④ + 答案文件 | `cards.html` 填写，导出 `answers.json` |
| 对齐 | example 预览 | ④ | `example.html`，页面顶部固定“示例 / 模拟 / 未验证”标识 |
| 规划 | 计划审阅 | ④ + ③ | `plan.html` 展示，并显示计划摘要码；批准在宿主确认框 |
| 验证 | workflow 图与试跑回放 | ④ | `replay.html` |
| 验收 | 验收清单 | ④ + 答案文件 + ③ | `acceptance.html` 勾选导出，签署走宿主确认 |
| 交付 | 验收单 / 交付报告 | ④ | `acceptance_sheet.html`（可打印为 PDF） |
| 运维 | 健康报告 | ④ | `fde check --report` 生成 `health.html` |

## 3. 产物规格

所有页面满足：单文件自包含（内联 CSS/JS，不加载外部资源）、可离线打开、生成时附 `generated_at`、`task_id`、`data_hash`，页面底部显示“该页面是只读快照，数据可能已更新”。

| 页面 | 业务专家视图 | FDE 工程师视图 | 关键要求 |
|---|---|---|---|
| graph | 业务对象卡片 + 关系 + 每对象一条已遮罩例子 | 表/字段/外键/接口 + 证据来源 | 每个元素有 `element_id`，可从业务视图跳到工程视图 |
| cards | 业务语言问题 + example + 选项（是 / 不是 / 不确定，说明） | 同一问题 + 技术证据 | 每张卡有 `card_id`；未回答的卡不得被默认为“是” |
| example | 样例输出 / 界面草图 / 模拟流程 | 同时显示依据的证据 | 显著标识非正式 |
| plan | “会做什么、对哪些对象、不会做什么” | 接口、参数、幂等、失败处理、回滚 | 显示 `plan_hash` 前 8 位摘要码，与宿主确认框核对 |
| replay | 业务步骤时间线 + 每步结果 | 每步请求/响应摘要 + 状态差异 | 数据已遮罩；失败步骤置顶 |
| acceptance | 业务验收项 | 工程验收项 | 两类分别由两类角色勾选 |
| acceptance_sheet | 范围、验收项、证据摘要、已知限制、签署人、批准引用 | 同左 + 技术附录 | 可打印；不含原始敏感数据 |
| health | 各交付物状态、最近运行、待处理事项 | 指纹差异、依赖状态、错误分类 | 与 `fde check` 输出同源 |

模式切换：页面右上角开关（业务 / 工程），只切换视图，不改变数据。

## 4. 回写协议（答案文件）

```text
cards.html（用户填写）
  → 下载 answers.json
  → 用户把文件路径或内容交给宿主（对话中说“已导出”）
  → fde answers import answers.json
       ├─ 校验 schema、task_id、card_id 存在、data_hash 与当前一致
       ├─ 若 data_hash 不一致：整份退回，提示重新生成页面
       ├─ 生成 DecisionRecord（source=file，card_id，答案，导入时间）
       └─ 事件 question.answered
  → 宿主更新能力图，并在对话里给一句摘要
```

`answers.json` 最小字段：`schema_version`、`task_id`、`data_hash`、`answered_at`、`mode`、`answers[]{card_id, choice, note}`。

**重要的诚实边界**：方案 A 的答案文件是普通文件，**无法证明由用户本人填写**，宿主 Agent 在技术上可以自行构造。因此：

1. `source=file` 的记录一律标注“用户经文件提交，未经可信确认”。
2. **凡是会影响下游写入动作的业务规则**（例如“金额超过某值必须人工”），在导入后由宿主以对话或原生确认**回显并让用户确认一次**，才升级为 `user_confirmed`。
3. 仅用于对齐和排序的低风险回答（如“这个字段是不是客户名”）可直接标为 `user_submitted`，但仍可被后续证据推翻。
4. Agent 不得代答问题卡；技能层规则中明确写出，并在门禁检查中核对“已确认项数量与 UI/对话回答记录一致”。

## 5. 架构与组件

```text
fde（CLI / stdio MCP）
 ├─ view     : 渲染器（输入 ViewModel JSON → 输出自包含 HTML）
 ├─ answers  : 答案导入与校验
 ├─ report   : 验收单、健康报告
 └─ 共享前端组件库 fde-ui-kit（渲染 graph/cards/plan/replay 等；与方案 B 共用）
数据：.fde/ 下的 SQLite + 版本化文件（D02，不变）
产物：.fde/projects/<id>/views/<timestamp>/*.html
```

**命令简表**

| 命令 | 作用 |
|---|---|
| `fde view <graph｜cards｜example｜plan｜replay｜acceptance> [--mode business｜engineering]` | 生成对应页面并返回文件路径 |
| `fde answers import <file>` | 导入答案文件 |
| `fde report acceptance` | 生成验收单 |
| `fde check --report` | 生成健康报告 |

产物目录定期清理（与 D03 的 TTL 一致），页面内不得包含原始敏感观测，只含遮罩后的结构和样例。

## 6. 安全要求

- 不监听任何端口；页面不发起网络请求（生成时扫描并断言无外链）。
- 页面内容经 HTML 转义，所有来自环境的文本按不可信输入处理，防止被观测数据注入脚本。
- 页面上**没有执行批准入口**。批准一律走宿主确认（L0），随后由 Harness 签发 L1 令牌（D06）。
- 计划摘要码用于“所见即所批”：页面显示的 `plan_hash` 摘要必须与宿主确认框展示的一致，不一致则拒绝。
- 验收单只含摘要和引用；签署人以宿主可信上下文中的用户引用为准。

## 7. 里程碑与验收

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 渲染器骨架 | ViewModel 校验、自包含 HTML 输出、双视图开关、`fde view graph` | 同一数据在两种视图下元素 ID 一致；页面离线可开且无外链 |
| M2 问题卡闭环 | `cards.html`、导出、`answers import`、data_hash 校验 | 过期页面被拒；未答卡不被默认；导入产生正确 DecisionRecord |
| M3 计划与回放 | `plan.html`（摘要码）、`replay.html` | 摘要码与宿主确认框一致性检查通过 |
| M4 验收与报告 | `acceptance.html`、验收单、`health.html` | 验收单字段齐全；健康报告与 `fde check` 同源 |
| M5 试点评估 | 在试点场景跑完整流程 | 采集基线：问题卡批量回答耗时、导入出错率、用户是否需要对照对话（不预设目标值） |

## 8. 风险

| 风险 | 缓解 |
|---|---|
| “导出再导入”让用户觉得繁琐 | 导出后页面显示一行可复制的指令；宿主可监听下载目录中的约定文件名（需用户授权） |
| 页面是快照，易过期 | 页面显示生成时间与数据哈希；过期时导入被拒并给出重新生成的指引 |
| 答案文件可被 Agent 伪造 | 见第 4 节：分级可信度 + 影响写入的规则必须回显确认 |
| 页面里的遮罩例子仍泄露信息 | 遮罩在渲染前由 Core 完成，渲染器不接触原始数据 |

## 9. 团队分工边界（并行开发）

| 模块 | 负责团队 | 与另一方案的关系 |
|---|---|---|
| fde-ui-kit（组件库） | **共建**，由方案 B 团队主维护 | 两方案共用，组件只依赖 ViewModel，不依赖是否有服务 |
| 静态渲染器、答案导入、报告生成 | 方案 A 团队 | 方案 B 复用其报告模板 |
| ViewModel / DecisionRecord / QuestionCard schema | **共同契约，单独评审**，变更需双方同意 | 见方案 B 文档第 3 节（内容与本节引用一致） |

## 10. 开放问题

1. 宿主能否在用户授权下读取下载目录中的答案文件，还是必须由用户手动给路径。
2. 验收单是否需要固定的客户模板（品牌、字段）。
3. 页面产物的保留期是否沿用 D03 的任务级 TTL。
