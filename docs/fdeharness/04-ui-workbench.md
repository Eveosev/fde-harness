# FDE Harness 交互与 UI 方案 B：本地工作台型

**版本**：0.1（并行开发用）　**日期**：2026-11-25
**组合**：1D 临时本地工作台　/　2C 宿主内摘要 + 工作台详情　/　3B 本地记录 + 可导出验收单（预留 3C 接口）　/　4C 交互式看板
**关联文档**：[PRD](01-product-requirements.md)、[架构](02-architecture.md)、[D01–D08 决策摘要](02-architecture.md#17-已采纳决策摘要与兼容约定)、[方案 A · 静态产物](03-ui-static.md)
**一句话**：用户显式启动一个只绑定 localhost 的临时工作台，问题卡、验收项、告警处理都可直接回写；执行批准仍然只走宿主原生确认。**需要修订 D02（见第 6 节）。**

---

## 1. 定位与适用

| 项目 | 说明 |
|---|---|
| 适用场景 | 问题卡多、需要频繁对齐的复杂交付；多个交付物需要持续运维看板的客户；目标用户主要是业务专家 |
| 核心取舍 | 用“一个受限的本地临时服务”换取真正的交互体验 |
| 不做什么 | 不常驻；不监听非回环地址；不承载执行批准；不做多用户协作 |
| 与方案 A 的关系 | 复用同一套 ViewModel 与组件库；A 的静态导出能力在 B 中保留，作为离线存档和降级路径 |

## 2. 交互通道总览

使用全部五个通道，其中通道 ⑤ 为工作台。

| 阶段 | 交互点 | 通道 | 方案 B 的实现 |
|---|---|---|---|
| 启动 | 选模式、说目标、授权范围 | ② + ③ | 同方案 A |
| 探查 | 进度与发现概况 | ② + ⑤ | 对话摘要；工作台“概览”页实时显示 |
| 建模 | 能力图浏览与修正 | ⑤ | 可展开、搜索、标记“映射有误”，修正写回候选映射 |
| 对齐 | 问题卡 | ⑤（少量仍可 ②） | 卡片流，逐张或批量，回答实时落库 |
| 对齐 | example 预览与反馈 | ⑤ | 预览 + “更接近 / 不对 / 想要这样”的反馈入口 |
| 规划 | 计划审阅 | ⑤ 展示 + ③ 批准 | 展示计划与摘要码；批准仍在宿主确认框 |
| 验证 | workflow 回放 | ⑤ | 时间线可逐步展开；失败步骤可标注“业务上可接受 / 不可接受” |
| 验收 | 验收清单 | ⑤ + ③ | 勾选实时写入，签署走宿主确认 |
| 交付 | 验收单 / 报告 | ⑤ 内导出 | 与方案 A 同模板 |
| 运维 | 交互式看板 | ⑤ | 交付物状态、漂移告警、待复验资产，可点进处理 |

## 3. 共享数据契约（与方案 A 文档一致，变更需双方评审）

两个方案**不得各自定义字段**。以下为最小共享对象，以 JSON Schema 为准。

| 对象 | 关键字段 |
|---|---|
| `ViewModel` | `schema_version`、`view_type`（graph / cards / example / plan / replay / acceptance / health）、`task_id`、`mode`、`generated_at`、`data_hash`、`elements[]{element_id, kind, business_view, engineering_view, evidence_refs[]}` |
| `QuestionCard` | `card_id`、`task_id`、`question`、`example_ref`、`options[]`、`evidence_refs[]`、`impact`（low / affects_execution）、`status`（open / answered / superseded） |
| `DecisionRecord` | `decision_id`、`task_id`、`card_id｜item_id`、`answer`、`source`（chat / file / ui / host_confirm）、`trust`（user_submitted / user_confirmed）、`user_ref`、`at` |
| `AcceptanceItem` | `item_id`、`kind`（business / engineering）、`criterion`、`evidence_refs[]`、`status`、`signed_by_ref` |
| `PlanSummary` | `plan_id`、`plan_hash`、`digest8`（摘要码）、`actions[]`、`object_set`、`risk`、`rollback` |
| 事件 | `question.answered`、`mapping.corrected`、`acceptance.item_checked`、`ui.session_started / ended` |

**组件库 `fde-ui-kit` 只依赖 ViewModel**：同一组件在方案 A 中由静态渲染器注入数据，在方案 B 中由服务端 API 注入数据。这是两队并行而不分叉的关键。

## 4. 工作台设计

### 4.1 生命周期

```text
用户（或宿主在用户同意后）运行 fde ui
  → 生成一次性会话令牌（有效期短，默认值试点确认），绑定本任务
  → 服务仅监听 127.0.0.1 随机端口，输出访问链接
  → 浏览器打开，令牌换取会话 Cookie（HttpOnly、SameSite=Strict）
  → 用户操作；每次写入产生 DecisionRecord 与事件
  → 用户关闭，或空闲超时，或任务结束 → 服务自动退出，令牌作废
```

### 4.2 页面结构

| 页面 | 内容 |
|---|---|
| 概览 | 任务目标、阶段、待办（待回答卡、待验收项）、最近事件 |
| 能力图 | 业务 / 工程双视图；元素详情带证据；可标记“有误”并说明 |
| 问题卡 | 卡片流；筛选“影响执行”的卡；回答实时保存；已答卡可修改并留版本 |
| Example | 预览、版本对比、反馈入口 |
| 计划与回放 | 计划摘要码、动作与对象、试跑时间线、失败标注 |
| 验收 | 业务 / 工程两类清单；签署跳转提示“请在宿主确认框中确认” |
| 运维看板 | 交付物状态、`fde check` 结果、漂移告警、待复验资产、RunSummary 趋势 |

### 4.3 与对话的同步

每次用户在工作台完成一批操作，Harness 向宿主推送事件，宿主在对话中给出一句摘要，例如“你确认了 12 项，其中 2 项与此前推断不同，已更新能力图”。**对话始终是主线，工作台是辅助。**

## 5. 安全设计（本方案的重点）

| 威胁 | 措施 |
|---|---|
| 服务被局域网或其他进程访问 | 只绑定回环地址；随机端口；校验 Host 与 Origin；一次性令牌；会话 Cookie 严格同站；关闭时令牌作废 |
| 跨站请求伪造、DNS 重绑定 | 校验 Host 头；写接口要求自定义请求头与 CSRF 令牌；不开启跨域 |
| 被观测数据中的恶意内容注入页面 | 所有来自环境的文本转义；严格的内容安全策略；不使用内联事件处理 |
| 宿主 Agent 代替用户提交 | 见下方“诚实边界” |
| 通过工作台执行高风险动作 | 工作台**没有任何执行入口**，计划页只有摘要码和“去宿主确认”的提示 |

**诚实边界**：宿主 Agent 通常有 Shell，理论上能读取令牌并调用本地接口，因此**工作台提交不能证明“由人点击”**。处理方式与方案 A 一致：

1. 工作台提交的是**业务判断输入**，不是执行授权；`source=ui`、`trust=user_submitted`。
2. `impact=affects_execution` 的卡，提交后仍由宿主回显并经原生确认一次，才升级为 `user_confirmed`。
3. 令牌只在用户可见的浏览器启动流程中使用，不写入宿主可读的日志；启动由用户或经确认的宿主动作触发。
4. 门禁检查核对“已确认数量”与工作台会话记录是否一致，异常则要求人工复核。

## 6. 对 D02 的修订（需评审通过后生效）

原 D02：“不提供本地 HTTP 服务”。修订为：

> 默认不开启 HTTP。`fde ui` 是用户显式启动的**临时、仅回环、一次性令牌**的本地服务；仅承载展示与业务判断输入的回写；**不承载执行批准**；任务结束或空闲超时自动退出；不对外暴露端口。

同时更新 D06 注：工作台不属于批准通道；L1 令牌只在宿主原生确认回执之后签发。

## 7. 技术形态建议

| 项目 | 建议 |
|---|---|
| 服务 | 随 Python 核心发布的轻量 ASGI 服务，与 CLI / MCP 共用同一实现层 |
| 前端 | 构建为静态资源随包分发，运行时不依赖外网；组件来自 `fde-ui-kit` |
| 接口 | 仅暴露读 ViewModel、写 DecisionRecord / AcceptanceItem / 映射修正；不开放任意文件或命令接口 |
| 实时性 | 首期用轮询或服务端推送均可，选更简单者；不引入消息中间件 |
| 降级 | 端口不可用或客户禁止本地服务时，自动退回方案 A 的静态产物 |

## 8. 里程碑与验收

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 服务骨架与安全基线 | 回环绑定、令牌、Host/Origin 校验、CSRF、超时退出 | 安全用例全部通过：非回环不可达、无令牌拒绝、跨站请求拒绝、退出后令牌失效 |
| M2 问题卡与能力图 | 卡片流、回答落库、映射修正、对话同步摘要 | 回答产生正确 DecisionRecord；对话摘要与实际变更一致 |
| M3 计划与回放 | 计划页（摘要码）、回放时间线、失败标注 | 摘要码与宿主确认框一致；页面无执行入口 |
| M4 验收与验收单 | 双角色清单、实时写入、验收单导出 | 与方案 A 验收单模板一致 |
| M5 运维看板 | 交付物状态、告警、待复验处理 | 与 `fde check` 同源；可点击进入复验流程 |
| M6 试点评估 | 完整流程试跑 | 采集基线：问题卡回答耗时、对话与工作台切换次数、误操作率（不预设目标值） |

## 9. 风险

| 风险 | 缓解 |
|---|---|
| 本地服务被客户安全策略禁止 | 自动降级到方案 A；客户评审材料中附第 5 节安全设计 |
| 工作台做大、侵占宿主主场 | 范围锁定为“看、答、验”；任何新增入口需评审；不做聊天、不做编辑器 |
| 用户误以为工作台里的确认等于批准 | 页面固定提示“这里不执行任何操作”；计划页只引导至宿主确认 |
| 前端维护成本 | 组件库共用；页面不含业务逻辑，逻辑留在 Core |
| 实时同步引入状态不一致 | 以 SQLite 为唯一事实源；工作台只读写 API，不缓存业务状态 |

## 10. 团队分工边界（并行开发）

| 模块 | 负责团队 | 与另一方案的关系 |
|---|---|---|
| fde-ui-kit | **方案 B 团队主维护** | 方案 A 复用；对外接口只依赖 ViewModel |
| 本地服务、会话与安全、看板 | 方案 B 团队 | 方案 A 不依赖 |
| 共享契约（第 3 节） | **双方共同评审，变更需双方同意** | 与方案 A 文档一致 |
| 验收单与报告模板 | 方案 A 团队主维护 | 方案 B 复用 |

**并行期间的两条纪律**：一是任何一方新增数据字段，先改共享契约再改实现；二是两方案的页面在同一份 ViewModel 夹具上都要能跑通，作为集成回归测试。

## 11. 开放问题

1. 令牌有效期、空闲超时的默认值（试点确认）。
2. 看板首期是否需要历史趋势，还是只显示当前状态。
3. 客户是否允许在受管设备上启动本地服务；受限时的降级体验是否可接受。
4. 3C（对接客户签署流程）的首个渠道，与 D06 的 L2 合并评估。
